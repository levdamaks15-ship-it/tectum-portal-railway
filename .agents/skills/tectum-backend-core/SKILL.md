# Инженерные стандарты бэкенда Tectum Portal

## 1. Архитектура точки входа и роутеров (Modular Routers Architecture)
- **`main.py` — строго Assembly Hub:**
  - Разрешена только сборка приложения: создание экземпляра FastAPI, подключение CORS/Middleware, монтирование статики (`/static`, `/uploads`), регистрация роутеров (`app.include_router`) и логика `lifespan()`.
  - **Категорически запрещено** размещать в `main.py` эндпоинты (`@app.get`, `@app.post`), Pydantic-схемы или прямую бизнес-логику.
- **Изоляция доменов:** Каждый модуль живет в своем файле (`routers/tasks.py`, `routers/checklists.py`, `routers/knowledge_base.py`, `routers/admin.py`).
- **Централизация общих зависимостей (`routers/common.py`):**
  - Межмодульные фоновые задачи (`BackgroundTasks`), функции `get_db()`, проверка сессий и общие утилиты централизуются в `routers/common.py`. Это исключает циклические импорты и `NameError`.
- **Развязка внешних интеграций:** Сетевые запросы к внешним сервисам (почта, синхронизации Google Sheets, сторонние API) запрещено выполнять на критическом пути транзакции; они обязаны выноситься в фоновые задачи (`BackgroundTasks`).

## 2. База данных, типы данных и автомиграции
- **Неограниченный `TEXT` для пользовательских заметок:**
  - Любые текстовые поля свободного ввода (описания задач, комментарии, аудит, примечания к сменам) обязаны иметь тип `TEXT`. Использование `VARCHAR(255)` категорически запрещено (исключение ошибок переполнения `StringDataRightTruncation` в PostgreSQL).
- **Автомиграции в `lifespan()`:**
  - При старте приложения схема проверяется и донакатывается безопасными запросами вида:
    `ALTER TABLE <table_name> ADD COLUMN IF NOT EXISTS <column_name> <TYPE>;`
- **Защита от N+1 запросов:**
  - При выборке связанных списков строго использовать жадную загрузку `selectinload(...)` или `joinedload(...)`.
  - Справочники перед циклами кэшируются в словарь в памяти (`dict`, доступ $O(1)$).
- **Атомарность транзакций (Atomic Mutations):**
  - Любые операции, модифицирующие несколько связанных таблиц, выполняются строго в единой транзакции (`db.begin()` или блок `commit()` с обработкой `rollback()`). Рассинхронизация связанных данных недопустима.
- **Инвариант UTC (Strict Server UTC):**
  - Сервер работает в UTC, завод — в UTC+5. Все даты и таймстемпы в БД и на бэкенде хранятся исключительно в UTC. Локализация часового пояса выполняется на стороне клиента.

## 3. Хронологическая сортировка смен в SQLAlchemy (Shift Sorting Order)
При написании любых SQLAlchemy-запросов к `models.Shift` (для списков смен, сводных таблиц, журналов, выгрузок в Excel или Google Sheets) **категорически запрещено** использовать ID записи (`models.Shift.id`) сразу после даты в `.order_by()`. Поскольку смены могут вноситься не по порядку или задним числом, сортировка по `id` приводит к хаотичным скачкам типов смен («День»/«Ночь») и номеров партий.

**Обязательные правила сортировки смен:**
- **Для списков и логов от новых к старым (`date.desc()`):**
  ```python
  .order_by(
      models.Shift.date.desc(),
      models.Shift.line.asc(),
      models.Shift.shift_name.desc(),
      models.Shift.batch_number.desc(),
      models.Shift.id.desc()
  )
  ```
- **Для графиков и хроник от старых к новым (`date.asc()`):**
  ```python
  .order_by(
      models.Shift.date.asc(),
      models.Shift.line.asc(),
      models.Shift.shift_name.asc(),
      models.Shift.batch_number.asc(),
      models.Shift.id.asc()
  )
  ```

## 4. Защита целостности, отладка и безопасный парсинг
- **Безопасный парсинг данных (`safe_int`, `safe_float`):**
  - При парсинге файлов Excel или текстового ввода числа обязаны приводиться через защитные конвертеры с нормализацией запятой (`str.replace(',', '.')`) для предотвращения `ValueError`.
- **Защита от 500-ошибок (Fail-Loud):**
  - Все эндпоинты оборачиваются в корректную обработку исключений с возвратом внятных HTTP-статусов (400, 401, 403, 404, 422). Запрещено возвращать «пустые» 500 ошибки.
- **Принцип отладки (Last Known Good State):**
  - При возникновении ошибки сначала найти и проанализировать последнее рабочее состояние (коммиты, бэкапы, логи). Установить точную причину, затем вносить правки. Не менять код наугад.
- **Очистка тестовых данных (Test Cleanup Invariant):**
  - Все тестовые данные, созданные автономными проверками API, обязаны немедленно удаляться из БД после завершения теста.

## 5. Универсальный шлюз безопасности и невидимость секретов
- **Серверный запрет на выдачу секретов (Backend Non-Exposure):**
  - PIN-коды, пароли, хэши и сессионные токены **категорически запрещено** отдавать в схемах ответов API (`GET /api/*`). Бэкенд возвращает только булевый статус: `has_pin: true`, `is_protected: true`.
- **Аппаратная проверка прав (Backend Authority):**
  - Скрытие кнопок в UI — только удобство. Любая операция модификации проверяет сессию и права на уровне API, отклоняя неавторизованные запросы кодом `403 Forbidden`.
- **Мягкое удаление (Soft Delete & Audit):**
  - Исторические и справочные данные не удаляются физически (`DELETE`). Используется флаг активности (`is_active = false`) и аудит в `AuditLog`.

## 6. Закон обязательного предварительного анализа уязвимостей (Pre-Flight Analysis)
Перед написанием кода любого нового модуля или рефакторинга агент обязан провести анализ по 5 направлениям:
1. **Безопасность и RBAC:** Защита от подмены ролей в `localStorage`/cookie, изоляция эндпоинтов `/api/admin/*`, достоверность авторства в `AuditLog`.
2. **Маршрутизация и сессии:** Исключение бесконечных циклов редиректа (`redirect loops`), синхронный сброс кук и токенов при выходе.
3. **Сохранность ввода (Zero Data Loss):** Защита активных форм от сброса при переходе между страницами (автосохранение в `localStorage`).
4. **Устойчивость верстки:** Проверка верстки при системном масштабировании Windows (125–150%) и на экранах смартфонов (360–414px).
5. **Фиксация в плане:** Результаты анализа уязвимостей обязательно вносятся отдельным разделом в `implementation_plan.md` ДО начала реализации.
